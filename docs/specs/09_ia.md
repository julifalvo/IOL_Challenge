# Spec 09 — Integración de IA (Task 07, 6 pts)

**Requisitos:** R-28..R-30 · **ADR:** 011 · **Prompts:** `prompts/instrument_enrichment_v1.md`, `prompts/eda_summary_v1.md`

El PDF evalúa **criterio de aplicación**, no complejidad. Componente principal dentro del pipeline + uno secundario de consumo.

## Componente A (principal) — Clasificación y enriquecimiento de instrumentos
**Problema:** 1.445 símbolos con descripciones truncadas e inconsistentes ("Cedear Bank Of America Corpora", "YPF", "Lt Rep Arg Cap V.29/05/26 $ Cg"). Las reglas cubren la mayoría, pero quedan casos `NEEDS_REVIEW` y atributos que las reglas no pueden inferir (emisor, sector, ticker del subyacente de un CEDEAR).
**Por qué IA acá:** es conocimiento del mundo + lectura de texto sucio; escribir reglas para cada emisor no escala y un analista tardaría horas. El resultado alimenta `dim_instrument` → mapeo a proveedor → cobertura de cotizaciones y cortes del EDA.
**Diseño:**
1. Input por subyacente, sin opciones: `symbol, description, currency, sibling_symbols (mismo underlying_key), rule_asset_type`. Las variantes reciben el mismo resultado. Solo metadatos de instrumentos: **ningún dato de clientes**.
2. Lotes de 50 símbolos, salida JSON validada contra schema (enums cerrados).
3. Política: la IA **no pisa** reglas determinísticas; solo completa `NEEDS_REVIEW` y campos vacíos. Si contradice una regla → `CONFLICT` en `ai_runs.validation_status` y gana la regla.
4. Caché por instrumento: clave = `sha2(input + prompt_version + model)`; rerun no vuelve a llamar (idempotencia y costo cero). Un lote fallido queda `FAILED` y se reintenta.
5. Evaluación a ciegas, sin `rule_asset_type` ni hermanos, para no inflar la cifra: muestra estratificada de 60 símbolos (`tests/fixtures/instrument_gold_labels.csv`, etiquetas escritas con asistencia de IA; ver ADR-011) → accuracy de `asset_type` y de `underlying_ticker_foreign`, para elegir el modelo; publicar en README.
**Ejecución (en orden de preferencia):**
- `ai_query()` en Databricks si el smoke test lo habilita (SQL-native, queda dentro del pipeline).
- Si no: script offline `tools/ai_batch/enrich_instruments.py` con la API de un modelo externo, o ejecución manual en un chat con el mismo prompt → JSON a Volume `landing/ai/` → notebook 09 lo valida e ingiere. Documentar que es la misma interfaz.
- Si no hay ninguna integración: modo diseño (prompt + output esperado de 10 símbolos + cómo se integra), válido según el PDF.

## Componente B (secundario) — Resumen ejecutivo del EDA
Input: `iol_ops.eda_metrics` (agregados de q1..q5, sin IDs de clientes). Salida JSON: `finding, supporting_metrics (claves del input), operational_implication, confidence, limitations, recommended_follow_up`.
**Validación post-LLM:** cada número citado en `finding` debe existir en el JSON de entrada (tolerancia de redondeo); si no, `validation_status = REJECTED`.

## Persistencia
`iol_ops.ai_runs`: `ai_run_id, pipeline_run_id, component, prompt_version, model, symbol, input_hash, output_json, validation_status, error, latency_ms, created_at`. `iol_ops.instrument_enrichment`: una fila por símbolo, solo salidas `VALID`.

## Limitaciones a documentar
- Conocimiento del modelo con fecha de corte: instrumentos nuevos o recién listados → baja confianza.
- No determinismo → mitigado con caché + versión de prompt + temperatura 0.
- Alucinación de emisores/tickers → mitigado con enums, validación contra reglas y muestra evaluada.
- La IA no decide calidad ni excluye filas: solo enriquece atributos descriptivos.

## Criterios de aceptación
- [ ] `asset_type` sin `NEEDS_REVIEW` y origen trazable (`RULE`/`AI`/`MANUAL`).
- [ ] Accuracy medida sobre muestra etiquetada.
- [ ] `ai_runs` con prompt_version y modelo.
